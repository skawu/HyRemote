# HyRemote v1.0.0.0 — release notes

Status: **candidate / acceptance pending**

This document describes the first HyRemote general-availability product generation. While the status line above is present, it is candidate material rather than a support declaration. The authorized `release/v1.0.0.0` PR must remain Draft during acceptance; after every mandatory gate passes, release finalization removes the candidate status before that PR may be ready for merge to `main`.

## Intended V1 product scope

HyRemote V1.0.0.0 productizes the x86_64 reference platform across Windows and Linux with three integration modes:

1. Embedded C++ through `HyRemote::RemoteAccess`;
2. Declarative QML through `import HyRemote` / QML `RemoteAccess` over the same runtime;
3. Transparent QPA Proxy for existing Qt applications with no HyRemote application linkage required.

Qt Widgets and Qt Quick are first-class application targets. The public contract remains transport-neutral and does not expose Core Session, capture, input, transport, RFB, or QPA-private implementation objects to normal applications.

## Simple V1 artifact model

The V1 release has one normal installed C++ target and payload-only declarative/QPA extensions:

- `hyremote-core` — static source/internal composition; **not installed/exported** as a V1 SDK target;
- `HyRemote::RemoteAccess` / `HyRemoteRemoteAccess` — the shared C++ product library and the one normal exported HyRemote CMake target;
- `qhyremote` — Transparent QPA platform MODULE payload, deployed through `hyremote_deploy(... QPA)` and **not exported as `HyRemote::QpaPlatform`**;
- HyRemote QML module — thin declarative payload over the same shared runtime; its backing library is not a second C++ SDK target.

`BUILD_SHARED_LIBS` does not switch the normal application between static and shared HyRemote product personalities.

Normal C++ use is intentionally small:

```cpp
HyRemote::RemoteAccess remote(&window);
remote.start();
```

Normal declarative use is likewise compact; actual runtime start is deferred until QML component completion so initial bindings can settle:

```qml
RemoteAccess {
    target: mainWindow
    enabled: true
}
```

Transparent QPA remains:

```text
MyApp -platform hyremote
```

## Reference environment

The V1 release is qualified against:

- Windows x86_64;
- Linux x86_64;
- Qt 6.8.3 for the integrated GA run;
- exact Qt 6.8.3 private ABI for Transparent QPA.

No broader Qt/QPA support claim is implied without separately accepted compatibility evidence.

## Product behavior

The intended accepted V1 behavior includes:

- inert construction for Embedded C++: no implicit listener;
- QML thin-wrapper lifecycle over the same runtime, with declarative `enabled: true` applied after component completion;
- loopback listener default;
- remote input disabled by default;
- explicit start/stop or explicit Transparent-QPA launch policy;
- remote view/input through one shared product runtime;
- reconnect without restarting the application where claimed;
- backend-neutral connected-client diagnostics distinct from lifecycle `Running` state;
- Widgets and Quick capture/input paths;
- one Transparent-QPA application session across supported multi-window/dialog/popup churn;
- installed SDK and source-consumption paths with the same public `RemoteAccess` target;
- one `hyremote_deploy()` entry point for C++, QML, QPA and combined QML/QPA packaging;
- deployed applications that do not rely on the original HyRemote SDK/build-tree runtime path;
- E1–E6 product examples/consumer evidence.

## Deployment boundary

Normal applications must not manually discover/copy Core, transport, RFB, capture/input adapter or other backend libraries.

- C++/QML deployment carries the one shared `HyRemoteRemoteAccess` runtime automatically.
- QPA deployment resolves the package-owned `qhyremote` payload plus that same shared runtime while the application executable itself remains Qt-only.
- The installed QPA package exposes availability/version/payload metadata to the deployment helper, not a QPA application link target.
- Linux QPA deployment uses controlled origin-relative/RPATH relocation rather than making `LD_LIBRARY_PATH` product configuration.
- A deployment that only works because an SDK/build directory remains on `PATH`, `LD_LIBRARY_PATH`, `QT_PLUGIN_PATH` or `QT_QPA_PLATFORM_PLUGIN_PATH` is not V1-acceptable deployment evidence.

## Security boundary

The current bounded RFB correctness baseline uses `SecurityType None`. It is therefore **not authenticated and not encrypted**. Loopback and view-only defaults reduce accidental exposure but are not substitutes for production authentication or transport encryption.

Do not expose the current baseline directly to an untrusted network or the public Internet.

## Transparent QPA boundary

Transparent QPA is a native-delegate-preserving proxy/decorator, not a replacement-only `qvnc` architecture. Native local display/input remains authoritative and remote access is additive.

V1 QPA support is intentionally version-coupled. Unsupported generic/foreign native surfaces and unqualified Qt/private-ABI combinations must fail or remain explicitly unsupported rather than silently degrading.

## Known unsupported or unverified areas

HyRemote V1 does not make product claims for:

- Embedded Linux / RK3588 / NXP platform lines;
- OpenHarmony;
- arbitrary Qt versions outside the accepted matrix;
- arbitrary native/foreign `QWindow` capture in Transparent QPA;
- zero-copy DMA-BUF, GBM, RKMPP, or other post-V1 performance paths as release requirements;
- Internet-safe authentication/encryption in the current RFB correctness baseline;
- a second static `RemoteAccess` product/distribution mode;
- any Windows/Linux/QPA row whose required executable evidence has not actually run and passed.

## Release process

The authoritative release flow is:

`feature/* -> develop -> release/v1.0.0.0 (Draft acceptance) -> release-note finalization -> main -> annotated v1.0.0.0 tag -> backmerge/v1.0.0.0 -> develop`.

The root CMake project version must match the release tag on the accepted release commit; feature/develop branches keep the development version sentinel until the release branch is cut.
