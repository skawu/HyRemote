# V0.2 technical preflight (#258)

Risk-removal record for the V0.2 line, run before any #143/#170/#174/#259 implementation work started. Each section
states what was measured, what it proved, and what remains open. Nothing here is a product feature: no TLS server, no
session registry and no non-loopback network policy was implemented.

Result: **PREFLIGHT_RESULT=GO**. Section A was settled by a real maintained viewer, section B by the focused OpenSSL
harness on both reference platforms, and sections C and D by repository audit; the one genuine architecture choice - the
TLS backend - was made by the owner on 2026-09-22 and is recorded in the last two sections.

**Reproduction.** `vncviewer64.exe localhost:<port> -SecurityTypes=X509Vnc -PasswordFile=<vnc passwd file>`, against the
spike server listening on that port with a self-signed certificate whose PEM was also placed at `<vnc config dir>/
x509_ca.pem`. Password-file bytes are the 8-byte password XOR `e84ad660c4721ae0`.

**Three wire facts the probe established, none of which were in the summary documentation we started from:**

1. after the server's sub-type list, the **client sends its own two version bytes** and only then reads the server's
   one-byte ack - sending the ack where the client's version belongs makes the viewer report "could not support the
   VeNCrypt version" and drop the connection;
2. before the client will create any TLS state it **reads exactly one byte** from the server: `0` means "server failed
   to initialize TLS session", anything else lets it handshake - without it both sides wait and the handshake times out
   (confirmed by peeking the socket: the client sent nothing at all);
3. the viewer's certificate trust comes from `X509CA` (default `<vnc config dir>/x509_ca.pem`) plus its per-host
   accepted-certificate store.

**Known gap, stated plainly.** The probe did **not** reproduce the legacy DES key derivation byte-for-byte, so the spike
accepted the response and continued. The viewer's response is demonstrably a function of the password file (different
passwords produce different responses to the same challenge), and the DES primitive itself is verified against two
published vectors; the derivation is therefore an implementation detail of #143's server side, not a viewer capability.
VIEWER_PROFILE_FEASIBLE is asserted on the negotiation, TLS and session evidence above.

## B. Qt TLS transition seam

**Target shape.** The accepted descriptor is owned by a `QSslSocket` from the moment it is accepted
(`QTcpServer::incomingConnection(qintptr)` -> `setSocketDescriptor()`), stays a plain stream for the RFB/VeNCrypt
preamble, and is upgraded with `startServerEncryption()` on that same object. No `QTcpSocket` is used first and no
descriptor is ever migrated between objects.

**Backend selection.** The owner's decision of 2026-09-22 makes OpenSSL the only qualified TLS backend for V0.2.0.0
`AuthenticatedEncrypted`. The harness selects it explicitly through Qt's own TLS-backend API
(`QSslSocket::setActiveBackend("openssl")`) *before* any `QSslSocket`, `QSslCertificate`, `QSslKey` or
`QSslConfiguration` is created, checks `activeBackend()`, and fails closed - reporting the profile as unavailable with
a non-zero exit - when the backend is not there. Running it on Windows without an OpenSSL runtime shows exactly the
failure mode the decision requires: `setActiveBackend("openssl")` returns false and `activeBackend()` stays on the
platform default, so nothing continues softly onto Schannel or onto a weaker profile.

**Evidence.** The focused lane `.github/workflows/tls-preflight.yml` runs `tests/preflight/test_qt_tls_transition_spike.cpp`
on both reference platforms with Qt 6.8.3. Run
[35674116424](https://github.com/skawu/HyRemote/actions/runs/35674116424) at `36af975`:

How each item required of this seam is produced rather than asserted:

| Requirement | Evidence |
| --- | --- |
| plaintext preamble really is plaintext | the server observes `ConnectedState` **and** `UnencryptedMode` while the banner and the VeNCrypt negotiation cross the socket, and records the byte count |
| same accepted socket transitions to TLS | `startServerEncryption()` is called on the `QSslSocket` that owns the descriptor from `incomingConnection(qintptr)`; the descriptor recorded before and after the transition is the same number on both platforms, and `BEFORE`/`AFTER` are printed so a reader can see it |
| TLS >= 1.2 configurable | the server requires `QSsl::TlsV1_2OrLater`; TLSv1.3 is negotiated, and a peer that offers only TLS 1.0 gets no session at all |
| server cert/key take effect | the credential material is generated inside the harness and loaded into the server's `QSslConfiguration`; the session only completes because they are valid |
| invalid cert/key rejected before exposure | six cases - valid, malformed certificate, malformed key, mismatched pair, missing certificate, missing key - and the listener is created for none of the failing ones. Qt cannot answer that question itself (`QSslCertificate::publicKey()` and `QSslKey::operator==` treat a matching public/private pair as different, which the harness verified first), so this uses OpenSSL's `X509_check_private_key`; if #143 keeps such a check it stays inside the Runtime transport and never reaches Core, the public API or the QML API |
| handshake timeout bounded | a peer that reaches the TLS phase and then sends nothing is released inside the budget, and the listener still completes a full session on the next connection |
| TLS error bounded, no fallback | a malformed TLS peer fails bounded with no plaintext continuation, no VNC-auth byte outside TLS and no weaker security type offered |
| reconnect clean | a second independent session establishes after the first ends; handshake counters show two |
| shutdown bounded, no late callback | the server is stopped during the plaintext phase, during the handshake and on an established session; each stop is bounded, every callback that arrives after the stop is counted, and the count is zero for all three |

**Two run-time facts the lane had to establish, kept here because a future re-run will meet them again.** A Windows
executable has no rpath, so Qt's and OpenSSL's `bin` directories must be on the loader path or the harness never starts
and reports `STATUS_DLL_NOT_FOUND` (`0xC0000135`) with no transcript at all - the first hosted Windows attempt failed
exactly that way. And a redirected stdout is fully buffered on Windows, so a process that fails fast loses every line it
had printed; the harness now writes unbuffered, which is what made the second failure legible.

**Where this leaves the seam.** The owner is decided: `TLS socket ownership`, `TLS config ownership`, certificate/key
loading, the handshake timeout and error translation all belong to the **Runtime transport implementation**, and the
OpenSSL dependency is an implementation detail of that layer. Nothing here requires a Core or public-API change, and the
harness itself is a standalone preflight project rather than part of the product build
(`docs/internal/repository-layout.md`).

## C. Runtime-private peer / session control seam

**Current ownership (from a repository audit).**

| Fact | Evidence |
| --- | --- |
| per-connection state lives in `RfbWorker::ClientState`, held in `std::unordered_map<QTcpSocket *, std::unique_ptr<ClientState>>` | `src/runtime/src/transport/rfb_transport.cpp` (map declaration and `emplace`) |
| a client is identified **only** by raw socket pointer - `ClientState` has no id or token field | same file, `ClientState` struct |
| handshake phases are explicit: `ClientPhase { AwaitVersion, AwaitSecurityChoice, AwaitAuthResponse, AwaitClientInit, AwaitInitialFrame, Normal }` | same file |
| held-input cleanup is already **transport-owned**: `RfbWorker::releaseHeldInput` decrements shared holder counters and publishes a release only for the last holder | same file |
| single-client teardown already exists **internally** on fault paths (protocol failure, auth rejection, handshake timeout, oversize input) through `deferClientAbort` -> `socket->abort()`; there is no external per-client API | same file |
| `Core::TransportEvent` carries `{ code, message }` only - **no connection identity** | `src/core/include/hyremote/core/transport.hpp` |
| `RemoteSessionId` does **not exist** anywhere; there is no admission concept | repository-wide search, zero matches |
| connected-client count is a **Runtime-owned** atomic mutated by the Runtime's own `ClientCountingTransport` wrapper | `src/runtime/src/access_instance.cpp` |
| the concrete transport is built privately and installed through `detail::createDefaultTransport` -> `session->setTransport(...)` | `src/runtime/src/detail/component_factories.*`, `access_instance.cpp` |

**Frozen seam.** A Runtime-private transport-control extension paired with the Core `Transport` object, not a Core
concept:

- `TransportPeerToken` — an opaque, transport-generated handle held by Runtime, never a socket descriptor, never a
  backend pointer, never equal to the public session identity, invalidated on disconnect so it cannot be reused across
  connections;
- `PeerAuthenticated(token, metadata)`, `PeerDisconnected(token, reason)`, `TerminatePeer(token)`;
- `RemoteSessionId` is created **by Runtime**, only after authentication **and** admission both succeed - never at
  accept time, and never by the RFB backend;
- held-input cleanup stays transport-owned (it already is), triggered by the same token;
- Core's frame/backpressure/session contract stays transport-neutral: no socket, no VNC client, no session registry in
  the Core stable contract;
- the control semantics are specified so a future non-RFB transport can implement them without RFB-specific concepts.

**Evidence status.** `PRIVATE_PEER_TOKEN_SEAM`, `RUNTIME_OWNS_REMOTE_SESSION_ID` and `HELD_INPUT_CLEANUP_TRANSPORT_OWNED`
are established by the audit above: every mechanism the seam needs already exists in private code (per-connection state,
one internal teardown path, transport-owned input release, a single composition point). A terminate-one-peer spike was
**not** run, and is deliberately left to #170, where the seam is implemented; the preflight freezes the shape and
confirms no architectural uncertainty remains.

## D. Typed Runtime notification seam

**Current polling (the thing being replaced).**

| Fact | Evidence |
| --- | --- |
| `Runtime::AccessInstance` is a plain class with snapshot getters (`state()`, `connectedClientCount()`, `lastError()`, `clearError()`) and **no signals at all** | `src/runtime/src/access_instance.hpp`, `access_instance.cpp` |
| the QML frontend polls it every **100 ms** (`m_pollTimer.setInterval(100)`, `Qt::CoarseTimer`) and refreshes exactly state, client count and error, emitting three **parameterless** signals | `src/integrations/qml/QmlRemoteAccess.cpp` |
| the C++ frontend (`HyRemote::RemoteAccess`) is a plain getter-only class with **no signals** | `src/integrations/cpp/.../RemoteAccess.h`, `remote_access.cpp` |
| Generic and QPA read state through `AccessController`; no polling, no signals | `src/runtime/src/automatic/automatic_access_controller.cpp` |
| the only cross-thread state today is the client-count atomic, written from the RFB worker thread | `access_instance.cpp` |
| no transport or Core notification reaches any frontend: `TransportEvent` is only counted/faulted in Core | `src/core/src/session.cpp` |
| the public surface is `HyRemote/RemoteAccess.h` plus the QML module; **no `QSsl*`, OpenSSL or transport type appears in any public header** | install rules and headers |

**Frozen seam.** Minimal and private, no event bus: `StateChanged`, `ConnectedClientCountChanged`, `ErrorChanged`, with
`AuthenticatedSessionEvent` reserved, delivered from the single `AccessInstance` truth to every frontend that needs
them. No stringly-typed topics, no global observer framework, no Rx-style layer, and no per-frontend state machine.

Threading and lifetime rules the seam must state:

- delivery happens on the ownering thread of the `AccessInstance` (the frontend thread today); the RFB worker thread
  must not invoke frontend code directly, so transport-thread facts are marshalled to that thread before delivery;
- observers register and unregister through the private seam only, and the `RemoteSessionId`/token objects are never
  handed to observers;
- after `AccessInstance` destruction no callback may run: the existing stop path (stop transport, quiesce, then release)
  is the guarantee, and the seam must preserve it rather than add a second lifetime;
- ordering between state, client count and error is defined by the seam, and repeated equal values are coalesced.

`TYPED_RUNTIME_NOTIFICATION_SEAM` and `NO_GENERIC_EVENT_BUS` are established by this audit; the spike for
"no callback after destruction" is left to #259, where the seam is implemented over the existing stop path.

### IMPLEMENTED_BY_#259

Implemented, verified on both reference platforms and merged; this section is the record of what the audit above
froze and what the implementation actually did with it. The audit's conclusions are unchanged.

```
NOTIFICATION_SOURCE=event-driven
DELIVERY_THREAD=producer/runtime thread
QML_MARSHAL=QObject owner thread
POLLING=removed
LIFETIME=bounded
ERROR_CLEAR=typed nullopt
SESSION_EXTENSION=reserved private typed extension
```

- **Where it lives.** `src/runtime/src/detail/runtime_notifications.{hpp,cpp}` holds one bounded, typed sink
  (`RuntimeNotificationSink`): three handlers (`stateChanged(AccessState)`, `connectedClientCountChanged(std::size_t)`,
  `errorChanged(std::optional<Error>)`), a subscription token, and `maxSubscribers = 8`. `AccessInstance` exposes only
  `subscribeNotifications()` / `unsubscribeNotifications()`; a frontend can subscribe but **cannot** publish, so there is
  exactly one source of truth for every value. No topic string, no variant payload, no observer base class, no global
  registry.
- **Event-driven, not relocated polling.** Notifications are published from the event boundaries the runtime already
  has: the start and stop lifecycle, a `ClientCountingTransport` wrapper, and an `ObservedCaptureSource` wrapper. Both
  wrappers hand the event to Core **first** and then publish the resulting truth, so the runtime observes what Core
  decided instead of racing it (a target loss therefore notifies `ErrorChanged`, then `Faulted`). The transport
  wrapper also observes the input path, which is where Core turns a throwing `InputSink::post()` into a recoverable
  error - the one error source that moves the occurrence revision.
- **Publication rule.** Every notification is a snapshot of the runtime truth taken after Core handled the event, and
  the sink drops a value the consumers already hold. A repeated state or an unchanged client count therefore delivers
  once; a genuinely new occurrence of the same recoverable error is delivered again (that is why its dedupe key is not
  just code/message/recoverable); `ErrorChanged(std::nullopt)` means "the effective error is gone" and is only sent
  while an error was previously delivered.
- **Stale events cannot pollute a newer run.** Each run has an activity token that `stop()` clears before teardown, and
  every wrapper checks it, so a late callback from a previous run is inert and a queued notification re-reads the
  *current* truth. This is the frozen "stale generation rejected" property, implemented without a per-notification
  generation field.
- **Ordering.** The snapshot publishes client count, then error, then state, so an observer that receives a state
  already holds the value that explains it. The exact sequences are frozen in the #259 ordering comment and asserted as
  sequences in `src/runtime/tests/access_instance_notifications_test.cpp`.
- **Delivery thread.** A notification is delivered on the thread that produced the fact (lifecycle caller, transport
  worker, capture/backend). The seam promises no GUI affinity; the QML wrapper marshals onto its own thread with a
  queued invocation whose context object is the wrapper, plus a `QPointer` guard, so neither a worker-thread
  notification nor a queued one that loses the race with destruction can touch a dead object.
- **Lifetime.** Unsubscribing stops further delivery; a handler that throws is contained per handler (it cannot escape
  into the runtime, abort a transport worker or change a Session state); and `AccessInstance` destruction cannot call
  back because the wrappers die with the Session that `stop()` already quiesced.
- **Frontend-local versus runtime error.** QML keeps its own validation error separate from the runtime's effective
  error and gives the local one priority, so an unrelated runtime event cannot erase what the frontend refused, while
  `clearError()` clears both.
- **Reserved extension point.** A typed authenticated-session callback can be added to this same handler bundle when
  #143/#170 land: it needs no Core change, no event bus and no change to the three existing notifications. Nothing
  session-shaped exists yet - no `RemoteSessionId`, no registry and no dummy event - because #259 must not invent one.

## Human decision (2026-09-22, recorded on #258)

```
DECISION=OpenSSL-only for V0.2.0.0 AuthenticatedEncrypted
SCHANNEL_STATUS=not qualified for V0.2.0.0
BACKEND_SELECTION=QSslSocket::setActiveBackend("openssl")
BACKEND_FALLBACK=forbidden
```

The decision is deliberately narrow: V0.2.0.0 qualifies the encrypted RFB profile only against Qt's **OpenSSL** TLS
backend on the Windows x86_64 / Linux x86_64 Qt 6.8.3 reference matrix; the Runtime selects the backend explicitly
through Qt's supported TLS-backend API before any `QSslSocket`/`QSslCertificate`/`QSslKey` use, rather than relying on
platform-default selection; if the OpenSSL backend, plugin or runtime is unavailable the capability fails closed as
unavailable and never falls back to Schannel, to a weaker security type or to plaintext; Schannel is not a V0.2.0.0
qualification target and dual-backend support is deferred unless later product evidence makes it necessary. TLS stays
Runtime/transport-private, so Core and public-API authority are unchanged by it.

`QT_TLS_BACKEND=openssl` is **not** a product mechanism and is not part of the frozen architecture. It was used once as
a diagnostic while isolating the backend; the mechanism that survives is the Qt API call above.

**What GO means, and what it does not.** It means the risks this preflight existed to remove are removed: the frozen
wire profile is consumable by a maintained viewer, the same-socket plaintext -> TLS transition works on the OpenSSL
backend on both reference platforms, the credential, timeout, failure and shutdown boundaries behave, and the private

#143 still has to implement the TLS transport, the session registry, admission and the non-loopback policy; #170 still
owns the peer-control seam and #259 the typed notification seam. It does not qualify Schannel, and it does not decide
anything about a machine without OpenSSL beyond the decided behaviour that the capability reports itself unavailable -
which is what the harness demonstrates by refusing to continue without the backend.
