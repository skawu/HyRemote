# V0.3.3.0 release remediation (2026-10-23)

## Status

```text
RETRACTED PUBLIC TAG/RELEASE = DELETED
CORRECTED RELEASE = IN PROGRESS ON release/v0.3.3.0
```

The old public tag and Release were deleted only under explicit one-time Owner authorization. This
document is the audit trail explaining why the rebuild is required.

## Findings

### Critical

1. The tag was created directly on `develop` without a `release/v0.3.3.0` branch, a release PR to
   `main`, a version bump, or a post-merge exact-HEAD tag.
2. The release notes were still marked `candidate` when the public Release was published.
3. Admission rows were assigned `3a65842` even though the viewer/auth/performance evidence was
   collected at multiple earlier SHAs. The same-SHA rule was not met.
4. The public GitHub Release was published as a normal release, not a draft or prerelease.

### Fixed during remediation

- The Windows L2 now prefers Git for Windows' real `bash` over the System32 WSL launcher, so the two
  governance self-tests run instead of being skipped: **85/85 PASS**.
- The release notes and admission record now carry an explicit retraction.
- The incorrect `3a65842` evidence attribution was removed from every admission row.

### Still open

- A single frozen candidate SHA must be selected and all required viewer/auth/performance rows must
  be re-run at that SHA.
- A proper `release/v0.3.3.0` branch must be created from the frozen candidate.
- Root CMake version is still `0.0.0`; release-version handling must follow the release procedure.
- Release PR, main merge, exact-HEAD annotated tag, and post-tag audit remain.
- The cursor visual limitation and the directional V0.3.0 comparison need explicit Owner
  ratification, not implicit acceptance.

## Corrected release procedure

1. Freeze one candidate SHA after all required evidence is re-run against it.
2. Create `release/v0.3.3.0` from that exact candidate.
3. Set the release version and remove the candidate marker from the release notes.
4. Open the release PR, pass Review Gate and the full **85/85** L2 on the release head.
5. Merge the accepted release PR to `main`.
6. Create the annotated `v0.3.3.0` tag on the exact accepted `main` HEAD without moving the
   retracted tag; use the next valid version name if the release authority does not permit reusing
   `v0.3.3.0`.
7. Run the post-tag audit and publish artifacts/checksums.
