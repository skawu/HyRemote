# Installed SDK Consumption

This guide describes the prebuilt/installed-prefix path. It is intentionally separate from source `add_subdirectory()` consumption.

## Contract

The V1 installed SDK exposes **one normal C++ product target**: `HyRemote::RemoteAccess`. That target is a shared library.

Core is statically composed behind the facade but is **not installed/exported** as a V1 SDK target. Transparent QPA is an optional plugin payload reached through `hyremote_deploy(... QPA)`, not an installed link target. The QML module is consumed through `import HyRemote`; its backing library is likewise not a second C++ SDK target.

Application code does not discover or link internal Core/transport/capture/input/QPA targets individually.

Point CMake at Qt and the HyRemote prefix:

```bash
cmake -S . -B build \
  -DCMAKE_PREFIX_PATH="/path/to/Qt/6.8.3;/path/to/HyRemote"
```

Then consume the package:

```cmake
find_package(Qt6 6.8 REQUIRED COMPONENTS Widgets)
find_package(HyRemote CONFIG REQUIRED)

target_link_libraries(MyApp PRIVATE Qt6::Widgets HyRemote::RemoteAccess)
```

For Quick, request the application's normal Qt Quick components and keep the same HyRemote product target. `find_package(HyRemote)` does not force an application to resolve Widgets, Quick or QML modules it does not use.

## Minimal application use

```cpp
#include <HyRemote/RemoteAccess.h>

HyRemote::RemoteAccess remote(&window);
remote.start();
```

Defaults are loopback, port 5900 and remote input disabled. Setters are optional policy controls, not mandatory setup.

## What `find_package(HyRemote)` means

`HyRemoteConfig.cmake` resolves the public dependencies of `HyRemote::RemoteAccess`, loads that exported product target, publishes optional QML/QPA payload metadata, and exposes `hyremote_deploy()`.

It does **not** turn Core, the QML backing library or `qhyremote` into application link choices. It is generated by HyRemote install/export rules; it is not expected to exist merely because a source directory was added to another project.

## Install from a HyRemote source checkout

```bash
cmake -S . -B build-hyremote -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH=/path/to/Qt/6.8.3/<toolchain> \
  -DCMAKE_INSTALL_PREFIX=/path/to/hyremote-sdk
cmake --build build-hyremote --parallel
cmake --install build-hyremote
```

The resulting prefix is then consumed with `find_package(HyRemote CONFIG REQUIRED)` as above.

To include the exact-version Transparent QPA payload in the SDK build, add:

```text
-DHYREMOTE_WITH_QPA_PROXY=ON
```

QML and other optional product payloads are enabled only when needed; their presence does not enlarge the normal C++ link surface.

## Deployment

One call owns normal runtime deployment:

```cmake
install(TARGETS MyApp RUNTIME DESTINATION bin)
hyremote_deploy(TARGET MyApp)
```

The helper composes with Qt deployment and adds the shared `HyRemoteRemoteAccess` runtime automatically. Applications do not copy that DLL/SO or any Core/backend file manually.

For a declarative application use `QML`; for a zero-source-change QPA application use `QPA`:

```cmake
hyremote_deploy(TARGET MyQmlApp QML)
hyremote_deploy(TARGET ExistingQtApp QPA)
```

See `docs/deployment.md` for the complete deployment contract.

## Validation fixtures

- `tests/consumer-installed-sdk` is the canonical clean C++ installed-prefix consumer.
- `tests/consumer-installed-qml` validates QML packaging without relying on SDK import/runtime paths.
- `tests/consumer-installed-qpa` validates that an ordinary Qt application has no HyRemote link dependency while deployment resolves the package-owned `qhyremote` payload.

V1 GA requires the deployed fixtures to run without relying on the original HyRemote SDK runtime path.
