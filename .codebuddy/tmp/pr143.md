## What this changes

The design step of `[SEC-01]` #143 (authenticated and encrypted transport), plus the correction of a statement that contradicted the release plan.

`docs/security-model.md` section 10 said authenticated/encrypted transport was "a post-baseline capability unless separately accepted into a later release", while `docs/development-roadmap.md` makes it a **V1.0.0.0 requirement, not a `V1.x` track**, sequenced design -> authentication -> encryption -> per-client authorization/audit. Two release authorities disagreed about what V1 means, which is the class of defect the converged scope authority exists to prevent. The roadmap governs, so the sentence is corrected and the design is recorded in place as section 10.1.

## The design that is now frozen, before any implementation

- **Authentication first**: RFB VNC authentication (security type 2), including the RFB 3.8 blind challenge, because that is what the mainstream viewers already implement. `SecurityType None` remains available but only as an **explicitly selected** mode - a client that does not select the configured type is rejected and the failure reported, never downgraded.
- **Encryption is a separate later step**, so viewer interoperability is not a precondition for the first authentication evidence.
- **OpenSSL** supplies DES/SHA-1 and TLS, rather than code written in this repository: a hand-written DES is a security anti-pattern. This is the repository's first third-party security dependency, carrying the package/`LICENSE`/`NOTICE`/deployed-payload obligations the release-readiness authority already anticipates.
- **Bind policy**: a non-loopback listener is accepted only while an authentication mode is enabled, and stays fail-closed otherwise - exactly what the existing guard `c2898c5` ("fail closed on a non-loopback listener until authenticated transport exists") was waiting for. Construction and listener defaults do not change.
- **Failure semantics**: bounded attempts, a bounded challenge/response exchange, no unbounded buffering, and the failure reported through `TransportEventCode::AuthenticationRejected` (already in the transport contract, currently a no-op) instead of being tolerated.
- **Authentication is not authorization**: the input policy boundary is untouched and view-only remains the default.

## What this does not do

It claims **no capability**. Until the authentication step lands, the stream remains unauthenticated and unencrypted, and every user-facing statement continues to say so.

It also does not move the gates: `SecurityType None` is machine-pinned by `tests/release-readiness/check_release_metadata.cmake` and `.github/workflows/git-flow-policy.yml`, and is stated in roughly twenty user documents. Those statements and gates move in the change that lands the capability, not in this one. That pinning is recorded in the design, because it makes landing authentication a coordinated documentation-plus-gate change rather than a code-only change.
