feat(api): notify Embedded C++ consumers instead of making them poll (#164)

The C++ facade had no way to learn that something happened: state(), connectedClientCount() and
lastError() had to be polled, and the shipped code indeed polls - the QML wrapper on a 100 ms timer,
the widgets example on another. The QML wrapper could at least expose signals on top of that; C++
consumers had nothing.

RemoteAccess stays a plain, movable value type, because docs/v1-api-stability.md freezes that and
forbids removing move support - which deriving from QObject would do. Its notifications therefore live
on RemoteAccessNotifier, reached through RemoteAccess::notifier():

    QObject::connect(remote.notifier(), &HyRemote::RemoteAccessNotifier::clientCountChanged, ...);

Every signal reports something that really happened, and none of it is produced by polling:

- clientCountChanged() comes from the transport's own connection events, through the decorator that
  already observes them;
- stateChanged() covers the transitions the facade causes and the ones it is told about, so a capture
  target disappearing or a component failing on a worker thread is reported too;
- errorChanged() is emitted whenever the diagnostic behind lastError() is written or cleared,
  including a recurrence of the same error, which an observer that acknowledged the first occurrence
  has to see.

To make the asynchronous half true rather than best-effort, Core gained Session::setChangeCallback().
It is deliberately small: only changes the owner cannot infer by driving the Session itself are
notified, because everything else happens inside a call the owner made.

Two defects were found by running the tests rather than by reading the code, and both are recorded
where they occurred:

- The first revision let the facade query the Session from inside Core's callback, which runs with
  Core's state lock held. Every getter takes that same non-recursive lock, so three facade tests hung
  until their timeouts exposed it. Core now hands the new state and diagnostic to the callback, and no
  callback path touches the Session.
- The connection decorator updated its count before forwarding the event to the Session. A signal
  emitted from there would have let an observer read pre-event values, so it now forwards first.

Verified: 50/50 in the default build, ten release gates, and a new notifier case that asserts a signal
for every real change and no signal when nothing changed. Two expectation bugs in that case were found
by measurement as well - an earlier publication had already reported the count, and Running ->
Stopping -> Stopped is genuinely two notifications.
