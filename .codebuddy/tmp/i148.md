## Goal

Make the embedded applicability of **Transparent QPA Proxy** explicit and decided, so a downstream integrator does not have to read `integrations/qpa` to discover that the mode cannot be used on an EGLFS-class target:

1. document the qualified native delegate set and state that an EGLFS/Wayland-class Linux target has **no delegate** for the QPA payload (i.e. `-platform hyremote` cannot start the application there, not merely "unverified");
2. stop presenting QPA as the embedded default in the cross-compilation guide for targets that have no qualified delegate;
3. record a scope/roadmap decision on a QEGLFS-style delegate (planned, or explicitly out of scope);
4. answer the embedded deployment question (application-local plugin directory; cross-compile-friendly payload list).

Reported from a downstream product integration (Huayan HMI, Qt 6.8.3 / RK3588 / EGLFS), verified against commit **4112ae6**. Not a V1.0.0.0 GA ask; we are **not** blocked — we ship Embedded C++ mode (see below).

## What we observed

### 1. On Linux the proxy delegates to `xcb` only

- `integrations/qpa/hyremote_platform_plugin.cpp:31-40` — `referenceNativeDelegate()` returns `"windows"` on Windows and `"xcb"` on Linux; there is no other candidate.
- `integrations/qpa/hyremote_platform_plugin.cpp:42-62` — a `delegate=` parameter is accepted only when it equals that reference delegate; anything else returns an empty name.
- `integrations/qpa/hyremote_platform_plugin.cpp:377-382` — the rejection path logs `HyRemote QPA Proxy rejected delegate; this build only permits xcb`, then `:384-392` creates the delegate through `QPlatformIntegrationFactory::create("xcb", ...)`.
- On an EGLFS-only rootfs (no `xcb` platform plugin, no X server) that factory call returns `nullptr`, so `createIntegration()` fails and the application cannot start at all.
- Note for reviewers: `integrations/qpa/hyremote_platform_plugin.cpp:75-77` implements `QNativeInterface::Private::QEGLIntegration`. That forwards *EGL native-interface calls* to the delegate and must not be read as EGLFS support — the delegate is still `xcb`-only.

### 2. The stronger fact is not in the user-facing documents

- `docs/known-limitations.md` §"Transparent QPA private ABI" names the delegate set and says "Do not infer compatibility with ... Wayland, EGLFS or a different native delegate"; `docs/compatibility.md:85` marks RK3588 / EGLFS as *Unverified*.
- Read together, an integrator concludes "unverified runtime behaviour". The actionable fact — **there is no EGLFS delegate on Linux, so the mode is not merely unverified but unavailable** — is only derivable from the plugin source.

### 3. The cross-compilation guide steers embedded users into QPA

- `docs/guide/cross-compilation.md:15-19` and `:52-55` make `--mode qpa` the default, including for `--toolchain cmake/toolchains/aarch64-linux-gnu.cmake` ("64 位 ARM 嵌入式 Linux（如 RK3588 类板卡）").
- `:80-84` shows `MyApp -platform hyremote` for the target, and §5 `:92` covers the version-mismatch plugin-load failure but not "there is no delegate for this platform".
- Result for an EGLFS target: the payload cross-builds (given exact 6.8.3 + `Qt6::GuiPrivate`), deploys, and then fails at application startup rather than at configure/build time.

### 4. Configure-time prerequisites are already good (not part of this request)

`CMakeLists.txt:110` (`find_package(Qt6 6.8.3 EXACT REQUIRED ...)`) and `:111-113` (explicit `Qt6::GuiPrivate` error) already fail fast with actionable messages. Recorded so this request is not misread as a build-DX defect.

### 5. QPA configuration is startup-only — as decided in #32

`integrations/qpa/hyremote_qpa_remote_controller.cpp:66-97` parses `hyremote-address` / `hyremote-port` / `hyremote-input` from the `-platform hyremote:...` parameter list. This matches the deliberate #32 statement that remote-input policy is a startup/relaunch policy. We are not asking to change it; see requirement 5.

## Why the product-model mismatch matters for embedded appliances

An HMI appliance that runs hardware video decode and exposes an **unauthenticated** (RFB `SecurityType` None) listener has a real interest in opening remote access **on demand** and closing it when idle — both for CPU/GPU budget and for exposure time. QPA's startup-time selection cannot express that (nor does it aim to), while Embedded C++/QML can.

Second aspect: QPA is a `plugins/platforms/qhyremote` MODULE with `INSTALL_RPATH "$ORIGIN/../../../."` (`integrations/qpa/CMakeLists.txt:19-30`), and `docs/known-limitations.md` §"Deployment scope" rejects deployments that only work through ambient `PATH` / `LD_LIBRARY_PATH` / `QT_PLUGIN_PATH`. `hyremote_deploy(... QPA)` then uses `file(GET_RUNTIME_DEPENDENCIES)` (`cmake/HyRemoteDeploy.cmake:78`, used by the QPA script at `:308`) and enforces exact Qt equality (`:241-258`) at install time — which cannot resolve target-architecture ELF dependencies when the install step runs on a cross host. For a cross-built appliance there is currently no documented "copy these files" payload list.

## Requested scope

1. **User-facing guide (Chinese primary + English mirror, per CONTRIBUTING):** in the QPA sections of `docs/guide/cross-compilation.md` / `docs/en/guide/cross-compilation.md` (and the mode guidance they reference), state the qualified delegate set and state that EGLFS/Wayland-class targets have no QPA delegate; make the embedded walkthrough either use `--mode cpp` / `--mode qml`, or explain the delegate requirement *before* showing `-platform hyremote`.
2. **Compatibility entry:** distinguish "no delegate on this platform" (unavailable) from "unverified runtime behaviour" for the QPA mode, so the mode decision is derivable without reading `integrations/qpa`.
3. **Decision record:** state whether a QEGLFS-style delegate payload is a post-V1 candidate (with its acceptance path) or explicitly out of scope, so downstream projects can cite the decision instead of re-deriving it.
4. **Embedded deployment answer:** is an application-local platform plugin directory selected with `-platformpluginpath` (not ambient `QT_PLUGIN_PATH`) acceptable for `qhyremote` in an embedded appliance? If yes, document the exact required layout; and either provide a cross-compile-friendly payload list (exact files to copy) or state explicitly that `hyremote_deploy(... QPA)` is desktop-install-only.
5. **If 3 is out of scope:** state in the user-facing guide that QPA is startup-selected by design and that products needing runtime enable/disable should use Embedded C++ / Declarative QML (which is what we did).

## What we did instead (we are not blocked)

- The consumer integrates `HyRemote::RemoteAccess` in **Embedded C++** mode: one `attachWindow(window)` plus explicit `start()` / `stop()`, with the runtime switch driven by environment variables (`ENABLE` / `ADDRESS` / `PORT` / `INPUT` / idle timeout) so the listener is closed by default and can be opened on demand.
- QPA is off in that build (`HYREMOTE_WITH_QPA_PROXY=OFF`); the only deployed extra artifact is the `HyRemoteRemoteAccess` shared runtime.
- Verified on x86_64 / Qt 6.8.3 (MinGW) against pin 4112ae6: viewer handshake and full-frame Raw capture (written to PNG and visually confirmed, not only counted), plus viewer click -> `QCoreApplication::sendEvent(window, QMouseEvent)` -> QML `MouseArea` (closed loop, coordinates in the window).
- Two integration notes that may be worth a line in the guides (not part of the request):
  - `hyremote::mapPointerToTarget()` expects source-frame **pixel** coordinates; an RFB client that sends `0..65535`-normalized pointer coordinates lands in a corner (we hit this and briefly suspected the adapter). One sentence in the viewer-connection doc would save that debugging session.
  - Raw-only frames make 1920x1080 roughly 8.3 MB per frame, which is the bandwidth tradeoff already tracked by #144.
