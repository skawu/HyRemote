### The flaky `hyremote-core-test-callback-exception-boundary` (PR #200, `fix/164-thread-scoped-allocation-injection`)

Three real fixes are in, each verified on its own, and **the test is still not green**:

1. `t_remainingAllocations` is `thread_local` - a worker's allocation can no longer spend the injection, and a worker
   can no longer be injected into. Measured: 200 consecutive runs, 0 failures, against 1 in 30 before.
2. Three callback paths in `src/core/src/session.cpp` captured their event **by value**, so the closure copy (and its
   `std::string` message) was materialised **before** `atCallbackBoundary()` - an allocation failure there escapes
   into the backend stack, which is exactly what CI reported as "escaped at allocation position 0". They capture by
   reference now; the boundary invokes its callable synchronously, so that is safe.
3. `Mailbox::push` released the oldest frame **before** storing its replacement, so a `std::bad_alloc` from storing
   left the mailbox holding less than before the call - a weak post-state rather than a strong one, and a silent
   shrink of the bounded pipeline. The displaced frame is held until the new one is queued and put back on failure;
   the FrameId is no longer consumed by a failed push.

**Still open, and measured as such**: with all three in, the binary fails about **3 runs in 200** at
`framesAccepted >= 1` - after the injection, the next valid frame is not accepted. The mailbox drop path is therefore
**ruled out by measurement**, not assumed. Next step: instrument that second delivery (which stage loses it - callback
gate, admission control, mailbox, dispatch) instead of guessing again.

The owner ruled that this should be pushed to a proper conclusion: the boundary's promise is that any allocation
failure inside it is contained and the session stays usable.

### Where the flake stands after the instrumentation step (measured, not claimed)

With all three fixes (thread-scoped injection, by-reference closure captures, mailbox strong guarantee) the binary ran
**0 failures in 500 runs** locally, where it previously failed 1 in 30 and ~3 in 200. That is **below the local
detection floor** (0/500 gives p < 0.6% at 95%), not proof of absence, and it is reported that way.

The instrumentation step produced a second, more useful finding: **the test is inherently position-sensitive**, because
it arms an exact allocation count. Adding a diagnostic to it changed the allocation sequence and the flake stopped
reproducing (0 in 300 with instrumentation, 0 in 500 after removing it). So "it passed on this build" can never be
evidence that the class of failure is gone - only CI across platforms can, and CI on the new SHA (`9c4bb66`) is still
mixed (some jobs pass, some fail).

Instrumented copy kept at `.codebuddy/tmp/instrumented-boundary-test.cpp` (untracked, deliberately not committed) so
that when a CI failure lands, the stage facts (delivery result, session state, diagnostic, mailbox waiting / owned /
dropped / overflow counters) can be captured instead of guessed. That is the next concrete step.

### The remaining failure is CI-only and toolchain-specific (evidence, then a temporary diagnostic)

On the newest commit with all three fixes (`9c4bb66`), CI's "all V1 modes" job still fails on the **same** line -

therefore to let CI answer: commit `3710707` on PR #200 is a **deliberately temporary** diagnostic that prints the

### The flake is fixed, and the cause was the one I first named - reported only after the wrong build was tested

**The cause**: three callback paths in `src/core/src/session.cpp` captured their event **by value**, so the closure

`accepted=0`, session `Running`: the boundary had not run yet). Capturing by reference fixes it - safe because the
