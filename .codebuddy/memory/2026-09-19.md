## The real root cause of the "hangs" the operator had to skip manually

`Start-Process -RedirectStandardOutput` hands the child a handle **that the command runner watches**, so the launching
command does not return until the application exits - 120-300 s for these runs - and reads as a stall. Two runs were
skipped that way, and I misread the skips as "the user chose background execution" and the approval timeouts as
intermittent. Both readings were wrong.

**Fix**: launch detached from Python - `Popen` with its own file handles, `stdin=DEVNULL` and
`creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` - which returned in under a second.
`.codebuddy/tmp/launch_showcase.py` is that launcher (it also puts `build-143c/remoteaccess` and Qt's `bin` on the child's
`PATH`, without which the payload exits silently with an empty log).

**Rules for next time**: never let measurement tooling hold the command runner open for the lifetime of the application
under test; launch GUI payloads detached and read results from persisted files; keep commands short when anything GUI is
involved; and read a backgrounded run's result from its record file rather than the console.

**Still owed**: the E2/E3 disable paths (payloads must be built; `qml-basic` additionally needs
`-DHYREMOTE_BUILD_QML_API=ON`) and the DPR interaction cell (needs a scaled or multi-display host).

## Retrospective: every command that went quiet for more than five seconds, and the fixes

Consolidated because this is a recurring operational failure, not a one-off. Five distinct causes, in order of damage:

**1. Process-lifetime coupling (the worst one).** `Start-Process -RedirectStandardOutput <app>` made the *launching* command
return only when the application exited - 120-300 s for these payloads - so it looked hung and the operator had to skip it
twice. Observed behaviour is consistent with the child holding the handle the command runner watches. **Fix, implemented and
verified**: launch GUI payloads **detached** from Python - `Popen` with its own file handles, `stdin=DEVNULL` and
`creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` - which returns in under a second
(`launch_showcase.py`, and the same pattern inside `e23_run.py`). **Rule: never let measurement tooling hold the runner open
for the lifetime of the process under test.**

**2. In-script silence.** Observer scripts slept through connection retries (2 s each), payload watchdog windows (14-45 s) and
action gaps without printing. Later scripts print a line per step (`say()` in `c_half.py`, `e23_run.py`); the earliest ones
(`a_half.py`, `held_stop_e2.py`) still had silent stretches. **Fix**: print a line before and after every wait, and run Python
with `flush=True` (or `python -u`) because redirected stdout is otherwise buffered.

**3. One long sleep instead of polling.** Several commands did `Start-Sleep -Seconds 240` and only then checked, so the
command was silent for minutes even though it was doing nothing. **Fix**: poll in bounded chunks (10-15 s) and print each
chunk's result, so the runner sees progress and the operator can stop it early.

**4. Silent child failure misread as buffering or a hang.** A payload exited immediately with an empty log because the
build-tree runtime directory was missing from `PATH` (Windows) - I read it as buffering and re-ran instead of diagnosing.
**Fix**: before any payload run, probe with a one-second self-terminating invocation and require exit 0 plus the expected
first line; and always read the *.err* stream as well as stdout (the QML payload writes its markers to stderr).

**5. Not a hang, but the same family of self-inflicted error: truncated output.** `Select-Object -First/-Last` censored the
GitHub comments list (wrong end), a branch count, and a gate's own failure reason, each time producing a wrong conclusion.
**Rule: read the whole listing or count it explicitly before forming a verdict, and read a tool's full error before naming a
cause.**

**Checklist to apply from now on**: launch detached; progress-print every wait; poll in chunks; probe silently-failing
executables on stderr and exit code before trusting their stdout; never truncate before concluding; and keep commands short
whenever anything GUI is involved.

### The checklist was not enough on its own - two of the fixes now exist as verified tools

The operator asked whether I had only self-reviewed without fixing. Correct challenge: only the process-lifetime fix had been
mechanised. Now in `.codebuddy/tools/` (deliberately not in the repository, since these are my own probes, not product
artefacts):

- **`run_detached.py <exe> --log <path> [--expect <regex>] [--timeout N] [--path <dir>]... -- [payload args]`** - launches
  detached with its own handles and process group, prepends the build-tree and Qt directories to the child's `PATH`, and then
  **probes**: it returns as soon as the expected first output appears, or, if the payload died, it prints the **exit code and

### REAL PRODUCT DEFECT FOUND: the Quick capture path applies the device pixel ratio twice

Found by the #162 non-1 DPR test the moment it ran with a real factor instead of 1.0.

exactly why this has been invisible: 1.0 squared is still 1.0, and **every existing test ran at DPR 1.0** (there was no
DPR assertion anywhere in the repository before this work).

**Location**: `src/remoteaccess/src/quick/quick_target.cpp:284-289` - `pixelSize` is built as

`QQuickItem::grabToImage(targetSize)` takes its size in **item (logical) coordinates** and applies the ratio itself, so the

### #164 first increment: the callback exception boundary, and the gap found by probing it

- **The finding was real, and the reason is precise**: `session.cpp`'s existing try/catch wraps `source->start()` /
  `transport->start()` themselves - an exception thrown *from* `start()` - not the later asynchronous invocations the
  backend makes into `onFrameReady`, `onCaptureEvent`, `onTransportEvent`. Those bodies do bounded bookkeeping that can
  allocate, so an exception there would unwind into code HyRemote does not own.
- **The repo already had the convention**: `onInput` contains the sink's exception and says so in its own comment
  ("the exception must not unwind through the transport runtime"), reporting a recoverable `ComponentFailure`. The new
  boundary is the same pattern applied to all four callbacks (`Impl::atCallbackBoundary` + `reportCallbackFailure`), and
  the handler deliberately does not allocate, because the failure it handles may be `bad_alloc`.
- **The injection test** (`src/core/tests/test_callback_exception_boundary.cpp`) replaces the global allocation function
  in that binary only and **sweeps** the injection position (0..63 frames, 1..31 capture events) instead of guessing one.

### The delivery hang is bisected: it needs an injected failure on a thread other than the caller

Recorded on PR #191 (`5740312120`), and it is a **mechanism, not a guess** - one variable was changed between the
hanging run and the clean one:

a `std::thread` function terminates the process - exactly what #164 acceptance criterion 2 forbids ("no `noexcept` path
can terminate the process because of an avoidable internal allocation/formatting exception").

### Worker boundary added (#164 criterion 2), and the hang is NOT an escaping worker exception

### #143 authentication stage: the authoritative map and the plan (owner picked this next)

The owner chose the **#143 authentication increment**: move RFB from `SecurityType None` to a real authentication
handshake. The authorities are `docs/adr/0006-authenticated-transport-design.md` and **`docs/security-model.md`
section 10.1**, which is the frozen design and where the interface/failure semantics live:

- **Mechanism**: RFB VNC authentication, **security type 2**, including the RFB 3.8 challenge/response and its
  blinding variant. `SecurityType None` stays available **only as an explicitly selected mode**: a client that does
  not select the configured type is **rejected and reported, never downgraded**. Encryption is a **later, separate**
  step. (The exact meaning of "blinding variant" needs to be pinned against the spec before implementing - I will
  not guess it.)
- **Failure semantics**: a bounded number of attempts, bounded challenge/response, no unbounded buffering, the
  connection closes on failure, and the failure is reported through the already-reserved
  `TransportEventCode::AuthenticationRejected` rather than tolerated. Authentication is **not** authorization.
- **Bind policy**: a non-loopback listener stays fail-closed **until an authentication mode is enabled**; with
  authentication enabled a non-loopback bind may be accepted, with it disabled it is still rejected.
- **Claim rule**: `SecurityType None` is pinned as a required phrase by `check_release_metadata.cmake:122-131` and by
  the release-policy workflow, and appears in roughly 35 user-facing documents/strings. The gates and those
  statements move **in the same change that lands the capability**, never in advance.

**Where the code actually is** (from a read-only exploration, all paths under the repo root):

- Handshake: `src/remoteaccess/src/transport/rfb_transport.cpp` - one security-type byte offered at `:592`
  (`const char security[] = {1, 1};`), only `1` accepted at `:603`, `SecurityResult OK` written at `:607-610`, phases
  in `ClientPhase` `:319-325`, handshake timeout `kHandshakeTimeoutMs = 3000` at `:32`.
- The VNC primitive already exists and is **only referenced by its unit test**: `src/transport/vnc_auth.{hpp,cpp}`
  (`generateVncAuthChallenge`, `computeVncAuthResponse`, `verifyVncAuthResponse`; `RAND_bytes`, DES ECB with the VNC
  bit order, `CRYPTO_memcmp`, `OPENSSL_cleanse`). It is compiled only when `HYREMOTE_TRANSPORT_SECURITY_AVAILABLE` is
  on, which is exactly what the OpenSSL option now controls.
- The configuration **never reaches the transport today**: the factory is `(const QHostAddress &, quint16)`
  (`detail/component_factories.hpp:44-46`), `createRfbTransport(address, port)`, and `loadSecurityDescriptor()` has
  **no production caller** - `RemoteAccess::start()` uses the profile only to *reject*
  (`remote_access.cpp:361-385`, `RemoteAccessErrorCode::SecurityUnavailable`). The public surface is
  `RemoteSecurityProfile` + `securityConfigFile()`; there is deliberately no `setPassword` property (a QML test
  asserts its absence).
- Test seams: real-socket handshake clients exist (`tests/test_rfb_multi_client_input.cpp:93-126`,
  `integrations/qpa/tests/rfb_test_client.hpp:86-134`, `tests/rfb_product_fit.py:45-63`), plus an in-memory
  `FakeTransport` installed through `component_factories.hpp:48-50` that can emit any `TransportEventCode`, including
  `AuthenticationRejected`.
- Pins to move with the capability: five test handshakes hardcode the byte `1`; `check_release_metadata.cmake:124`
  requires the phrase in every milestone note; `examples/remote-support-showcase/main.cpp:116-119` shows it in a UI
  string; the rest are prose.

**Plan (todos in the tool)**: (1) plumb the profile + loaded credential into the transport factory; (2) implement
security type 2 - offer only the configured type, 16-byte challenge, verify, SecurityResult, bounded failure with the
reserved event; (3) deterministic handshake tests (success, wrong credential, unselected type, bounded); (4) the
non-loopback bind rule; (5) move the gate phrases and the ~35 statements in the same change.

### #143 authentication: the mechanism is in and the suite is green, but the increment is not finished

Slices 1 and 2 of the plan are implemented on `build/143-simplify-openssl-provider` (same branch as the S1
simplification, so PR #198 currently carries both - they may need splitting before review):

- The **frozen wording correction** the owner ruled on: `docs/security-model.md` section 10.1 no longer says "the
  RFB 3.8 challenge/response and its blinding variant". The RFB specification defines no such variant (checked against
  the community spec, 224 KB, which has no "blind" anywhere and lists type 2 simply as VNC Authentication), so the
  text now states the random-16-byte challenge and the DES response, and says why the earlier wording was removed.
- **The configuration reaches the transport at last**: `RfbSecurityConfig { vncAuthenticationRequired, password }`,
  carried through `TransportFactory`, `createDefaultTransport` and `createRfbTransport` into `RfbWorker`;
  `RemoteAccess::start()` now really calls `loadSecurityDescriptor` (which returns
  `std::optional<SecurityDescriptor>` and is move-only - my first call assumed a different signature). With the
  capability absent from the build it still refuses with `SecurityUnavailable` **before** reading the descriptor,
  which keeps "never a weaker listener" true in both configurations.
- **The handshake implements security type 2**: exactly one type is offered and it is the configured one (`None` only
  when the insecure profile asked for it), a fresh random 16-byte challenge is sent, the 16-byte response is verified
  through the existing `vnc_auth` primitive, `SecurityResult` is written, and a failure is reported through
  `TransportEventCode::AuthenticationRejected` with the abort deferred exactly as `protocolFailure` does it. Bounded
  by construction: one challenge per connection, no retry, and the existing handshake timeout closes a stalled
  client.
- **The old pin moved with it**: `test_remote_access.cpp` asserted `SecurityUnavailable` for a secure profile with a
  descriptor path; it now expects `InvalidConfiguration` because the descriptor is really parsed.
- **A trap worth keeping**: `HYREMOTE_HAS_TRANSPORT_SECURITY` is a **private** compile definition of the runtime, so
  the test executable did not see it and took the "capability absent" branch, failing one assertion. The test now
  gets the definition from the same CMake variable (`HYREMOTE_TRANSPORT_SECURITY_AVAILABLE`) that drives the library,
  so the two cannot disagree.
- **Evidence**: capability ON (Qt SDK's OpenSSL), configure succeeds, build 0 errors, **51/51** tests pass.
- **Still owed before this can be called a capability**: the deterministic handshake tests (success, wrong credential,
  unselected type, bounded), the non-loopback bind rule, and - most importantly - the claim move the ADR requires in

  default (insecure) statements remain true but the secure profile's new behaviour is unclaimed and untested.

### #143 authentication: the handshake is now measured, and measuring it found a real protocol defect

Slice 3 is done: `src/remoteaccess/tests/test_rfb_vnc_auth_handshake.cpp` drives a real socket through the whole
configured VNC authentication exchange. It is gated on the capability (like the primitive's own test) and picks its
port the sanctioned way - a probe `QTcpServer` binds port 0 and the transport is told the number it got, so nothing in
the file chooses a port. Cases: the correct credential gets `SecurityResult OK`; a wrong credential gets
`SecurityResult failed`, the reserved `AuthenticationRejected` event and a closed connection; selecting `None` while
authentication is configured is refused rather than downgraded; a client that stalls after the challenge is closed by
the handshake bound; and the insecure profile still offers `None` and completes.

**The test found a real defect on its first run**: the failure path wrote `SecurityResult failed` and then aborted the
socket, and the four bytes never reached the client - the peer saw an abrupt reset instead of the protocol's own
failure answer, which the RFB specification requires. Fixed by flushing that result with a bounded wait
(`kHandshakeFlushMs = 1000`) before the deferred abort, on the failure path only.

Two test-side lessons, both about time: `waitForDisconnected` returns **false** when the socket is already
disconnected, so "the connection closed" must be asserted as `state() == UnconnectedState || waitForDisconnected(...)`;
and a transport event is published on the worker thread, so the client can observe the closing connection before the
handler has run - the recorder therefore waits for the event with a bounded poll instead of asserting immediately.

Evidence: capability ON, build 0 errors, **52/52** tests, ten release gates pass. Remaining: the non-loopback bind
rule (slice 4) and the claim/gate move (slice 5), which is what makes the secure profile claimable at all.

### #143 authentication: the bind rule is explicit and tested (slice 4)

`remote_access.cpp` used to allow a non-loopback listener for a secure profile only because nothing rejected it - the
rule existed as an absence of code. It is now one explicit decision, taken after the credential is in hand:

- `authenticationEnabled` is set only when a descriptor was really loaded (so a configured profile that failed to
  produce a credential can never widen a listener), and a single trailing check reads
  `if (!authenticationEnabled && !m_impl->listenAddress.isLoopback())` -> `InvalidConfiguration`, message contains
  "non-loopback". This implements `docs/security-model.md` section 10.1: closed until authentication is enabled, then
  allowed.
- `test_remote_access.cpp` gained `testBindPolicyFollowsAuthentication()`: the insecure direction is refused with
  nothing composed, and with the capability in the build a `QTemporaryDir` fixture (password.txt "secret7" plus a
  descriptor naming it) makes the **same** non-loopback address accepted, with the transport factory observed to
  receive `vncAuthenticationRequired == true` and a 7-byte password. `RuntimeCounters` records the flag and the
  password **length** only - a test that echoed a secret into its output would be the leak the security model forbids.
- **Sensitivity probe**: temporarily changing the check to reject every non-loopback address made exactly this test
  fail (5 CHECK failures at the secure half), so it genuinely detects a regression in the rule rather than passing
  vacuously. Restored: build 0 errors, **52/52**, ten gates.
- Also confirmed by reading, not assuming: the credential requirement was already enforced by the descriptor loader
  (`passwordFile is required for authenticated security profiles`, empty password and >8 bytes rejected), so no new
  check was needed there.

### The CI flake: root cause found, fixed and pinned by a test (PR #200)

- **Symptom**: #198 and #199 red **only** on `hyremote-core-test-callback-exception-boundary` (`src/core`, which
  neither branch touches), with mixed pass/fail at the **same SHA**; 1 failure in 30 local runs of that binary, and
  the local failure was a *different* case (line 113, frames not accepted) than CI's (the capture-event case at
  position 0).
- **Root cause** (read from the code, then measured): the injection was a **process-wide** allocation counter, while
  a Session really runs a scheduler thread and a dispatcher thread (`src/core/src/session.cpp:999-1002`). A worker's
  allocation while armed spent the injection, so the swept positions stopped testing the contract they claim, and a
  worker could be injected into at all.
- **Fix** (PR **#200**, branch `fix/164-thread-scoped-allocation-injection` from `develop`, commit `e3df1fb`, one test
  file, no production code): the counter is `thread_local` ("armed" = the next allocation by the arming thread), a
  deterministic case `coreAllocationInjectionIsScopedToTheArmingThread` (started Session + another thread allocating
  inside the armed window) fails **every time** against a process-wide counter, and the mechanism is in comments.
- **Evidence**: 200 consecutive runs, **0 failures** (was 1 in 30); probe with a process-wide counter fails
  deterministically in exactly the new case; full suite 50/50; gates 10/10.
- **Two traps hit while writing that case, worth remembering**: constructing a `std::thread` **allocates on the
  creating thread**, so it has to happen outside the armed window; and a `std::string` built from a **constant size is
  folded away** at release optimisation, so the probe must call the replaced allocation function directly.
- **Owner rulings this round**: fix the flake in its own develop-based PR; and merge **#198 first, then #199** (with
  #199's base retargeted to `develop` once #198 lands).
- **Chain in progress**: #200 (green → merge) → rerun #198's failed jobs → merge #198 → retarget #199 → rerun →

### Product review the owner asked for: convenience and over-design (measured, not opined)

**Golden path, measured**: consumer CMake 11 lines (3 of them product), minimal C++ use 4 lines
(`RemoteAccess remote(&window); remote.start();`), one public target, one `hyremote_deploy()` call, facade header 127

**Convenience gaps found**:

1. **The C++ facade has no signals and no `Q_OBJECT`** (grep-verified) while the QML wrapper has 12 `NOTIFY`

3. The examples are acceptance instruments (131/214/233/274 lines, of which 5-15 are actual HyRemote usage, plus

4. Default port 5921 is not the VNC convention (5900/5901), so a viewer user types the port - accepted trade-off

**Over-design: surface larger than substance** (the feature set itself is justified):

- 16 configure options visible for a product that needs zero, with internal switches (`BUILD_CORE`,

descriptor-file indirection (keeps secrets out of argv/QML and is not readable back), release profiles derived from
the project version (not a user knob). The gates are heavy but their cost is maintainer-side - the one maintainer cost
worth naming is that they pin implementation text verbatim, which this session paid for more than once.

### The CI flake was NOT fixed by thread scoping alone - two causes, one still open (#200)

**Correction to my own note above.** The thread-scoped injection did not make
`hyremote-core-test-callback-exception-boundary` green. CI, with the scoping fix compiled in (the failure moved to line
167 of the new file, proving it was the fixed binary), still reported `escaped at allocation position 0`, and locally the
same binary still fails about **2 runs in 100** at `framesAccepted >= 1`.

**Cause 1, found and fixed**: three callback paths in `src/core/src/session.cpp` captured their event **by value**
(capture-event :947, input :1081, transport-event :1088 as they were), so the closure copy - including the event's
`std::string` message - was materialised **before** `atCallbackBoundary()` was entered. An allocation failure there
escapes into the backend stack, which is exactly what the boundary exists to prevent. They capture by reference now,
which is safe because `atCallbackBoundary` invokes its callable synchronously (`:335-342`).

**Cause 2, still open**: an allocation failure on the **frame** path can leave the session unable to accept the next
frame (`framesAccepted >= 1` fails). The test cannot go green until that is answered, and answering it is a
product-quality decision - how far the boundary's promise extends - so it was put to the owner rather than decided
here.

**PR #200 was retitled and its body rewritten to say this plainly**, because it no longer claimed to fix the flake. Two
lessons worth keeping: a plausible root cause that explains *a* failure is not proof it explains *the* failure, and a
fix must be validated by the same measurement that found the problem (here: the CI log of the fixed binary). The
`mark_as_advanced` ordering bug in PR #201 and the `std::endl` flush bug in the same PR came from the same family.

- **Environment trap worth remembering**: a fresh CTest run fails every executable with `0xc0000135`
  (STATUS_DLL_NOT_FOUND) unless the **build tree's DLL directories** are on `PATH` in addition to Qt's `bin` - and CMake's
  compiler test silently fails with no diagnostics unless the mingw `bin` directory is on `PATH` too.

## What `remote-support-showcase` actually is (asked directly, answered from the repository)

Not an opinion question, so the answer came from measurements:

- **Self-description**: `examples/remote-support-showcase/README.md:3` - "This example demonstrates the V1.0
  production-facing remote-support workflow through the public `HyRemote::RemoteAccess` facade only."
- **Not a delivered artifact**: it lives under `examples/`, and `cmake/HyRemoteProjectOptions.cmake:7` defines
  `option(HYREMOTE_BUILD_EXAMPLES "Build HyRemote examples" OFF)` - so it is **not built by default** and has **no
  install rule** (only `examples/qml-basic` and `examples/qpa-proxy-existing-app` document one). It does not ship.
- **But it is a repository acceptance payload**: `docs/repository-layout.md:64` - "The acceptance suite is E1-E6:
  `widgets-basic`, `quick-basic`, `qml-basic`, `qpa-proxy-existing-app`, `remote-support-showcase`, and the
  installed/source SDK consumers." It is driven by `.github/workflows/v1-ga-acceptance.yml` and by
  `tests/product-e2e/showcase_product_fit.py`, and it is even referenced by
  `tests/release-readiness/check_release_metadata.cmake`.
- **How the docs present it**: `docs/product-overview.md:119` calls it "a **production-like** remote-support showcase";
  `README.md:199` and both install guides list it as an example built according to the enabled integration packages;
  `docs/v1-ga-acceptance.md:127` has a dedicated acceptance section for it.
- **Conclusion**: it is the **example that demonstrates the product-facing workflow** and a **verification vehicle** -
  the product-facing part is the workflow it demonstrates, not the program itself. It is **not** a productised debugging
  tool and not part of the payload. That is consistent with the earlier ruling that made 5922 a fixed
  observation-only port rather than a member of the product-default tier.
- **Found while checking**: the showcase README illustrates the CLI with `--port 5901`, which will be confusing once 5921
  is the product default. Ruled into **#179** by operator decision: it becomes `--port 5922` labelled
  verification-only, and the item's "8 documents" becomes 9 (the showcase README was not part of the `5900` count -
  its literal is `5901`). Rationale recorded: the showcase is the **E5 acceptance cell**, so a wrong port in its
  documentation harms acceptance repeatability.
