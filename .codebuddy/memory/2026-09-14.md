## SPIKE-02 / issue #16 — public asynchronous capture path evaluated (host)

Main had moved to `a25332b` (SPIKE-01 accepted, squashed via PR #15). Executed issue #16 on a
**new branch off main**: `spike/16-async-capture` (3 commits), Draft PR
https://github.com/skawu/HyRemote/pull/19, status envelope on issue #16 (comment
5662501239). New harness `spikes/async-capture/` (21 evidence JSONs), new doc
`docs/async-capture-spike.md`, cross-links in `docs/capture-spike.md` and
`docs/compatibility.md`.

Key results (public API only, `QQuickItem::grabToImage()`):

- **Composition trap solved**: the QML root item is a *child* of
  `QQuickWindow::contentItem()` (per `qquickview.cpp`), so root-item grabs miss overlay/popup
  siblings (3.31 % differing pixels vs the sync capture, **0.00 % outside the overlay rect**).
  Grabbing **`contentItem()`** is pixel-identical to `grabWindow()` for 2D and Quick3D
  (max channel diff 0) and within 2 for a custom-FBO scene.
- Mechanism (source-backed): `create()` + DirectConnection to `beforeSynchronizing`
  (QSGLayer setup) and `afterRendering` (render + `toImage()` readback on the render thread),
  completion posted to the GUI thread as `ready()`. `create()` rejects (null result +
  qmlWarning) when the item has invalid dimensions, is not attached to a window, or its
  window is not visible.
- **Pipelining does not add frames**: distinct ticks = requests/K, duplicates =
  requests - requests/K, average tick lag = (K-1)/2; completions are FIFO; nothing is dropped.
  A paced control (one request per frame) gives 0 duplicates and 0 lag.
- Throughput 26.7 /s (K=1) → 152.4 /s (K=16); latency 32 → 102 ms; GUI jitter 1.8/12.2 →
  36.9/92.9 ms. No built-in outstanding-request limit (one QSGLayer per request).
- Memory bounded, not leaking: +45.5 MiB for 1000 requests vs +0.9 MiB in the no-capture
  dry-run control (+43.9 MiB at 240 requests → plateau).
- Backpressure must be caller-imposed: unbounded production retains 36 MiB and would drop
  ~87 % of frames for a 10 /s consumer; a consumer window of 2 bounds it at 9 MiB.
- **The async path does not suffer the D3D11 stall**: 115.5 captures/s at K=4 where the
  synchronous `grabWindow()` collapses to 1.1 iterations/s in the same session.
- Three gaps left open (not solved, not worked around): visible-window precondition
  (hidden window → null result, no callback; the sync path still captures it on this host);
  `QOpenGLWidget` has no public async API at all; `QQuickWidget` exposes only its embedded
  Quick content asynchronously (`grabWindow()` on its render-control window returns null), so
  whole-window composition stays synchronous.
- **No GL/PBO/render-thread/RHI code was written**, because the public path already meets
  composition/Quick3D/FBO fidelity and the widget-target gaps were not shown to be material
  against any frame budget.

Harness pitfalls worth remembering (cost time):

- `QQuickItem::mapTo()` does not exist; the method is `mapToItem(const QQuickItem*, QPointF)`.
  It maps through the scene, so it also works for siblings.

## CORRECTION — PR #19 Round-1 review found a BLOCKER in the slow-consumer probe

Owner review comments `5662534191` (BLOCKER + two doc boundaries) and `5662540092`
(positioning of `grabToImage()`). Correction pushed to the same Draft PR #19
(https://github.com/skawu/HyRemote/pull/19#issuecomment-5662851185); Issue #16 envelope
updated (comment 5662855136). Commits `661eae2`, `ca43f0f`, `b79b571`. PR stayed Draft, no new
PR. Nothing from #17, no GL/PBO/RHI/private API, no VNC/RKMPP/QPA/Core API.

The two probe defects (both in the harness, not the API):

1. `releaseAfterNs = readyNs + consumerDelayMs` was computed **per frame**, so several frames
   were "consumed" in parallel — that never modelled one serial 10 fps consumer;
2. the admission check was evaluated **once per loop slice** and up to `maxInFlight` requests
   could still be issued afterwards, so retained frames overshot the configured window by up to
   K (observed `maxHeldObserved = 4` at window 2).

Corrected model (now in `spikes/async-capture`): **one serial consumer** — completed frames
enter a single queue, the consumer services one frame at a time for `--consumer-service-ms`
(100 ms → 10 fps), `nextServiceStart = end of previous service`, so services never overlap.
`--consumer-window` → `--completed-queue-capacity`: the capacity bounds **queue depth**
strictly and the in-service frame is owned in addition, so the ownership bound is exactly
`capacity + 1` (documented in doc, README and every report). Three producer policies are
measured separately so capture is not stopped to fake a transport drop policy:
`none` / `drop-oldest` (latest-frame-wins) / `producer-throttle` (admission control; counts
in-flight requests so the bound holds).

Corrected numbers (quick2d, K=4, one serial 10 fps consumer):

| strategy | producer /s | consumer /s | drop ratio | max queue | max owned | peak retained | max stale |
| unbounded | 116.9 | 9.7 | 0% | 55 | 56 | 123 MiB | 55 frames (5.8 s behind) |
| drop-oldest cap 2 | 119.3 | 9.9 | 90.8% | 2 | 3 | 6.6 MiB | 2 frames (170 ms) |
| producer-throttle cap 2 | 9.8 | 9.5 | 0% | 2 | 3 | 6.6 MiB | 2 frames (195 ms) |

Invariants now checked: `maxQueueDepthObserved <= completedQueueCapacity` holds exactly;
consumer rate 9.4-9.9 /s against the 10 fps target; `delivered + dropped == completed` in every
configuration (the no-consumer configurations count completed frames as delivered).

Doc boundaries narrowed: the validated composition claim is **same-scene sibling content under
`QQuickWindow::contentItem()`** (the `Popup.Item`/`Overlay` parent chain) — `Popup.Item` is an
architectural inference, `Popup.Window`/`Popup.Native`/Control-specific `Popup`/`ToolTip` are
unverified; only `hide()` was tested, so `minimized`/occluded are unverified; `grabToImage()`
is positioned as the **public-API asynchronous baseline / v0.1 candidate**, not the final
high-performance path (Qt warns the offscreen render + GPU→CPU copy is costly).

Also recorded: the `-all` runs re-measure the sync baseline in a warmer process state and are
load-sensitive (`customfbo` 39.69 ms / 13.2 /s vs 15.86 ms / 30.1 /s in its dedicated run;
customfbo pipeline cadence 38.4 /s in `-all` vs 137 /s earlier). Dedicated per-scene files are
authoritative; both figures are now reported as ranges.

## CORRECTION — Round-2 review: timestamp/freshness semantics were reversed

Owner review `5663534836` (PR #19): backpressure PASS, but the timestamp/freshness wording had
the sign backwards. Correction pushed to the same Draft PR (comment 5663684291); Issue #16
envelope updated (comment 5663688292). Commits `dd0be55` (harness definitions) and `3cb8413`
(doc + README). **No measurement was re-run** — no schema key, formula or report changed, so the
files the review validated stayed byte-identical. Nothing from #17, no GL/PBO/RHI/private API.

The semantic rule (now stated in `docs/async-capture-spike.md` §5.5, the harness header, the
JSON emission sites, the README metric table and the PR body):

```
scene-state advance (request -> captured image) = tick in image - tick at request
```

- A **positive** value means the captured image carries a scene state **newer** than the state
  at the moment the request was issued: the request was served by a later render. **Not** an
  age, **not** staleness. For K>1 all pending requests are served by one later shared render, so
  they all get that newer state (average advance is exactly `(K-1)/2`).
- Banned phrasings (they were wrong): "lags the request", "never newer than the request",
  "up to K-1 ticks old". The request-to-image relationship is about **correspondence**, not
  freshness.
- **Timestamp contract (ARCH-01 input):** the request timestamp is **not** a valid content PTS
  for `grabToImage()` under pipelining. v0.1 baseline = **completion / `ready()` timestamp**
  (also when the buffer enters the caller's ownership); request time is kept only as a latency
  diagnostic; a backend that can observe the real rendered/presented frame time may supply a
  more accurate PTS; the generic Core must **accept** a PTS from the backend, not derive it from
  the request.
- `consumer.staleFrames*` (`producedSoFar - frame index`) is a **request-sequence age**, never
  visual content staleness. The visual age of delivered pixels is **not measured** by any probe
  in this spike. Accepted freshness evidence for drop-oldest = queue depth / owned-frame bound,
  completion-to-service wall-clock age (21.8 ms avg / 170.2 ms max), producer/consumer rates,
  delivered/dropped accounting, plus the separate request-to-image scene-state advance.
- Report keys were intentionally **not** renamed (`content.tickLag*`, `consumer.staleFrames*`)
  so the already-reviewed evidence stays valid; both the doc (§10) and the README carry a
  key-definition table stating what each key actually holds.
