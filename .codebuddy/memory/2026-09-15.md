### Core invariants worth keeping in mind for #6/#7/#9

- `RemoteFrame` lifetime anchor is `std::shared_ptr<const FrameStorage>`; frames without
  storage/geometry/planes are rejected at acceptance. `CpuFrameStorage` runs an optional
  release hook exactly once from its destructor (hook must not throw). Producer-side writes go
  through `CpuFrameStorage::mutablePlane()` **before** publication.
- Timing: `FrameTiming{pts, ptsSource, requestTime?, completionTime?}`. `Completion` derives the
  PTS from `completionTime`; an explicit `Render`/`Presentation` value is preserved; a declared
  backend source **without** a value is rejected (not relabelled); a frame that only has
  `requestTime` is rejected. `FrameId` is assigned inside the mailbox at push time = acceptance
  order (never request order). This is the ARCH-01 timestamp rule in code.
- `Damage` tri-state; `Damage::fromRegions({})` is `Regions` with no rectangles — explicitly not
  `Unknown`. (The ARCH proposal's `Damage::regions()` factory cannot compile against the
  `regions` member; renamed to `fromRegions()`.)
- Backpressure: `detail::Mailbox(capacity, policy)`. Capacity counts **waiting** frames; the
  dispatch-worker-owned frame is additional → peak Core-side ownership `capacity + 1`.
  `DropOldest` (latest-frame-wins) is default and counted, never an error. `ProducerThrottle`
  admission counts `waiting + inFlight < capacity` (same rule as PR #19 round 2).
- Threading: capture completion only validates/stamps/enqueues; a single dispatch worker is the
  only `Transport::enqueueFrame()` caller and holds no Core lock across it. Adapter exceptions on
  Core threads are caught → counted → `Session` goes `Faulted` (never terminate the host).
- Lifecycle: config/capability errors leave the Session `Stopped` (fail before `Starting`);
  component startup failure leaves it `Faulted` until `stop()` (then `Stopped`). `stop()` order:
  stop scheduling → `source->stop()` → close+drain mailbox → join workers → `transport->stop()`.
  `stop()` is idempotent and `noexcept`.
- `SessionStats` is the adapter/test observability surface (in-flight, accepted, dropped,
  dispatched, mailbox gauges, lastFrameRejection).

## ANALYSIS - can HyRemote's remote-access route serve the OpenHarmony Qt platform?

User asked whether the technical route can satisfy OpenHarmony, referencing `openharmony-sig/qt`. No code
change; the answer is an assessment.

Facts established (from the project's own README on the archived Gitee mirror; the gitcode Wiki is
client-rendered and could not be fetched, so nothing about the QPA plugin/graphics stack/limitations is
asserted): Qt for OpenHarmony = patches + adaptation modules on a **Qt 5.15.12** baseline (8 patched
submodules: qtbase, qtdeclarative, qtmultimedia, qt3d, qtwebview, qtsensors, qtconnectivity,
qtquickcontrols), contribution via `patch/v5.15.12/<submodule>.patch`, repo moved from Gitee to GitCode,
licenses Apache-2.0 plus Qt's LGPL/GPL family.

Assessment: the route's *shape* fits a QPA-integrated platform exactly (target-attached public-API
capture, protocol-neutral VNC/RFB transport, Qt-level input, optional version-coupled QPA proxy mode,
backend-pluggable acceleration), which is why no OS-specific capture/injection API is needed. The real
blocker is the version gap: HyRemote requires Qt 6.8+ while the port is Qt 5.15.12, so it cannot run
there today; after that come unverified capture/input behaviour on that QPA (offscreen layers, grab
paths, input path via ArkUI), the patch-based port being a moving target, OHOS-native buffer models
instead of GBM/DMA-BUF for zero-copy, the OHOS NDK/HAP toolchain and packaging, and the mixed-license Qt
build for distribution under the dependency policy.

Recommended: keep the published roadmap position (OpenHarmony long-term, not a gate), resolve the Qt
version strategy first (wait for/contribute to a Qt 6 port, or a Qt 5.15 adapter experiment), then run a
bounded feasibility spike whose evidence feeds `docs/compatibility.md` (stay `Unverified` until then).
Offered to record this as `docs/openharmony-qt-evaluation.md` + an Issue, but did not touch the repo since
PRs #54/#55 are awaiting owner review.

**R2-B1 — teardown ownership was not atomic.** `stop()` checked `teardownStarted` under the mutex,
released it and only set the flag later inside `teardownRun()`, so two callers could both break out
and race on the same component stop / worker `join()`. Fixed with a claim taken **while holding the
mutex** (`claimTeardownLocked`: sets the flag *and* `++runGeneration` in one critical section);
`stop()` blocks in `claimTeardown()` and then either finds the run `Stopped` (releases the claim so
other waiters finish) or owns the teardown. `teardownRun()` snapshots `sourceStarted` /
`transportStarted` / `workersCreated` under the mutex and clears those flags, so every component and
worker is cleaned by exactly one side. `SessionStats::teardownsPerformed` makes it observable
(must be exactly 1 per run).

**R2-B2 — stop() during Starting could be undone by the in-flight start().** `start()` released the
mutex around component `start()` calls, so after a completed stop it could resume and publish
`Running` again. Fixed with a **run generation**: `start()` claims `generation = ++runGeneration`,
and re-checks it (check + commit in the same critical section) at the gate installation, the source
start, the worker creation (mailbox + both threads created under the mutex so a teardown never sees
a half state), the transport start (checked before, committed after) and immediately before
publishing `Running`. A cancelled `start()` stops exactly the component that completed startup after
the cancellation, reports the new `SessionErrorCode::StartCancelled` and returns false without ever
publishing `Running`; whatever was committed before the claim is stopped by the teardown instead.

**Control evidence** (same approach as Round 1, worth reusing): with the old non-atomic claim the
barrier case fails on `teardownsPerformed == 1`; with the boundary checks removed both
start-cancellation cases fail on `!started`. Both controls reverted, tree clean.

Tests: 68 cases / 9 targets, 0 failures, stable over 8 runs; full root with spikes 23/23.

### Two environment traps hit during this round (cost real time)

1. **`Copy-Item` preserves the source mtime**, so restoring a file from a backup leaves the file
   *older* than the compiled object and **ninja skips the rebuild** — I then "measured" a control
   build's behaviour while believing it was the restored code, and the R2-B2 tests appeared to fail
   for no reason. Always touch the restored file (`(Get-Item f).LastWriteTime = Get-Date`) or force a
   rebuild before re-running.
2. **`setvbuf(stdout, NULL, _IOLBF, 0)` is invalid on MSVC**: with a null buffer only `_IONBF` is
   allowed, otherwise the invalid-parameter handler fail-fasts the process (exit `0xC0000409`) before
   any output. Every test binary crashed with no output until this was changed to `_IONBF`.
3. `replace_in_file` silently failed again twice (one added `fprintf` never landed; one removal needed
   a second attempt). Grep after every edit, especially after "successful" ones.
